# Первый этап: состояние реализации

Ветка `feature/monitoring-service`, исходная точка `38e9f92`. Пользователь выбрал последовательную реализацию службы, установщика, настроек и заготовок PawnIO/температур. Сам драйвер и датчики не устанавливались.

## Реализовано

- Native LocalSystem service, AUTO start через setup; сбор по подключению, grace 5 секунд, lease 15 секунд, единый ETW collector.
- Ограниченный протокол и local-only pipe с ACL, проверка PID сервера по SCM. GUI использует mailbox последнего значения; зависший UI перестаёт подтверждать подключение.
- DiskIo и TCP/UDP IPv4/IPv6 декодирование с TDH-проверкой схем, PID+creation time, история TID. Потери ETW сбрасывают историю и приводят к перезапуску; умерший consumer повторно запускается с задержкой.
- Setup с UAC и встроенным бинарным payload; установка, обновление, enable/disable/remove. Защищённые каталоги, запрет reparse paths, порядок отката stop → restore → restart.
- Шестерёнка внизу, статусы и диагностика, действия службы, предложение настройки при подтверждённом отсутствии. GUI manifest asInvoker; setup requireAdministrator.
- TemperatureSource, SensorReading/scopes, PawnIoState/ownership, неподдержанные действия драйвера и явная заглушка в UI.

## Проверено

Release GUI/service/setup и target monitoring-package. 14 CTest executables, включая реальные local pipe операции, geometry/offscreen GUI и регрессии независимого ревью. Манифесты извлечены из готовых EXE. Service зависит только от ADVAPI32, tdh и KERNEL32. SHA256 встроенного service resource совпал с собранной службой. Скрипты PowerShell прошли синтаксический разбор.

Независимое ревью выявило шесть важных проблем: loss → stale identities, unbounded queued GUI snapshots, неработающий restart consumer, преждевременный RUNNING, rollback работающего image, неограниченное ожидание ETW stop. Исправлены одним проходом с red/green регрессиями; повторное независимое ревью не выполнялось.

## Принятые изменения плана

1. Только этап A по последнему запросу пользователя. Температуры остаются недоступны до этапа B.
2. OpenThread fallback не используется: неразрешённая атрибуция остаётся неполной. Цена — часть событий может не попасть в счётчик; угадывания владельца нет.
3. Вместо соседнего payload с каталогом хэшей service встроен в setup; native CRT статический. Пакет больше, зато нет изменяемого файла между проверкой и копированием.
4. Результат setup приходит через process handle/exit code ShellExecuteEx и повторную SCM-проверку. Цена — подробные этапы транзакции не передаются; отдельный код обозначает неполный откат.
5. Исторический EtwIoProbe сохранён как прототип. Новый MonitorProbe проверяет производственный IPC, а не дублирует collector. Его PASS не доказывает корректность всех byte counts.
6. Системные и нагрузочные проверки пока не выполнены. Скрипт измерения реализует только три парных idle-интервала службы; Build/Copy/Network, GUI/system CPU и throughput ещё не автоматизированы. Нельзя считать A8 завершённым или обещать процент накладных расходов.

## Осталось проверить с отдельным разрешением на системные изменения

Установка/удаление на Windows, UAC cancellation/другая учётная запись, перезагрузка, два GUI, реальная атрибуция диска и TCP/UDP IPv4/IPv6, проверка rollback занятого файла и расходы ETW. Обычные CTest не изменяли SCM, Program Files или драйверы. Подписание наших EXE сертификатом не выполнялось.

## Уточнение диагностики после пользовательского запуска

На пользовательском скриншоте служба 1.0.0 подключена, потери ETW и ошибки схем равны нулю,
но общий счётчик несопоставленных событий достиг 3777. Общий счётчик не позволял отличить
несопоставленные операции диска/сети от ошибок жизненного цикла процессов/потоков.

В версии службы 1.1.0 / протоколе 2 добавлены фиксированные счётчики восьми причин:
отсутствующий/неизвестный TID диска, отсутствующий/неизвестный PID сети, ошибки OpenProcess
и GetProcessTimes, время создания процесса новее события, неизвестный владелец потока.
Настройки и MonitorProbe показывают суммы и последний интервал, несопоставленные байты,
последний PID/TID и код Windows. Начальное заполнение таблиц также учитывается.
Ошибки жизненного цикла сами по себе больше не помечают оба источника Partial;
несопоставленные операции влияют только на свой источник. Защита при реальных потерях ETW сохранена.

Проверены Release-сборка, 15/15 CTest, визуальное отображение тестовых данных и прокрутка
настроек в небольшом окне. Независимое ревью не выявило Critical/Important;
найденная неточность TID у событий процесса исправлена с red/green проверкой декодера.
Добавлены проверки передачи End-событий и позднего дискового I/O после переиспользования TID.

Пакет размещён в `D:\Projects\QTaskManager\build\monitoring-1.1.0`;
SHA256 трёх EXE совпадает с результатами сборки. Установленную службу этот проход не обновлял:
нужно открыть новый GUI и выполнить «Настройки → Обновить» с UAC.
Точная причина прежних 3777 событий пока не установлена; её можно исследовать по новым
счётчикам после обновления. Процент дополнительных накладных расходов не измерялся.

## Основная колонка: файловые запросы процесса

Пользователь выбрал «В основной колонке показывать файловый I/O процесса» после наблюдения
физического I/O преимущественно у System. В службе 1.2.0 / протоколе 3 сбор переключён на FileIo
Read/Write через FILE_IO_INIT; физические DiskIo-события больше не включаются и не суммируются.
IoSize и TTID проверяются по TDH с учётом v2/v3 и x86/x64. Используется время запроса;
отклики диска и HighResResponseTime к файловым запросам не применяются.

Колонка «Файлы, MB/s» и подсказка сообщают смысл размера запрошенных данных и работу через кэш.
Настройки и MonitorProbe используют ту же семантику. FileIo-события иных типов отклоняются
до mutex; имена из таких событий не разбираются и не сохраняются, стеки и ETL не собираются.
Память под диагностику остаётся ограниченной.

Release и 15/15 CTest проверены, включая регрессию TTID приложения при заголовке System,
четыре независимых макета FileIo, неподдержанные схемы и исключение физических событий.
Независимое ревью сверило макеты с Microsoft TraceEvent; Important/Critical не найдено.
Пакет: `D:\Projects\QTaskManager\build\monitoring-1.2.0`. Для использования нужно обновить службу
из нового GUI. Реальные кэшированные нагрузки, TDH на пользовательских событиях и CPU-overhead
этим проходом не измерены. Восстановление причинного процесса для всех memory-mapped/системных
записей не обещается.
